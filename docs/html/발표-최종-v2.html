07
Existing Solutions

이미 나와 있는 해결책들, 이렇게 작동합니다

조사 대상 몰 추천 · 리뷰 · 사이즈표

아무도 이 문제를 방치한 게 아닙니다. 세 가지 방식이 이미 쓰이고 있고, 각각 실제로 효과가 있습니다.

Solution A

몰 자체 사이즈 추천

무신사 등은 내 구매 이력을 근거로 "당신은 이 상품 L"을 알려줍니다. 이력이 쌓인 사용자에겐 꽤 정확합니다.

작동 원리 · 같은 몰에서 산 옷의 사이즈 패턴

Solution B

비슷한 체형 리뷰

"175/70인데 L이 딱 맞아요" 같은 체형 후기를 참고합니다. 사람이 직접 쓴 실착 정보라 신뢰감이 있습니다.

작동 원리 · 나와 비슷한 사람의 경험 대입

Solution C

상세 사이즈표(cm)

브랜드가 부위별 실측치를 공개합니다. 숫자가 있으니 이론상 가장 정확한 정보입니다.

작동 원리 · 옷의 실제 치수 공개

공통점
셋 다 "옷 쪽 정보"이거나 "남의 몸 정보"입니다 — 정작 내 몸은 아무도 모릅니다
08
The Limits · Root Cause

그런데 새 브랜드로 넘어가는 순간, 셋 다 멈춥니다

5 Whys 근본원인

왜 안 되는지 다섯 번 파고들었더니, 세 해결책의 한계가 한 지점으로 모였습니다.

Limit A

그 몰 안에서만 작동

구매 이력이 있어야 추천이 나옵니다. 처음 가는 몰·처음 보는 브랜드에서는 아무것도 나오지 않습니다. 정작 그때가 제일 불안한데도요.

이력 없음 = 추천 없음
Limit B

남의 체형은 내 기준이 아니다

같은 175/70이어도 어깨·가슴·배 비율이 다릅니다. 그래서 후기마다 말이 갈리고, 많이 볼수록 더 혼란스러워집니다.

표본이 늘어도 확신은 안 늘어남
Limit C

숫자는 있는데 대조군이 없다

사이즈표는 정확하지만 내 몸 치수를 모르면 읽을 수 없습니다. "가슴단면 52cm"가 나에게 큰지 작은지 판단할 기준이 없습니다.

읽을 줄 몰라서 못 씀
Root Cause
브랜드를 가로질러, 지금 내 몸을 기준으로 번역해주는 곳이 없다

문제 ①에 대한 답소요 약 2분

몸을 재서 옷을 찾는 게 아니라, 평소 잘 맞는 옷에서 몸을 거꾸로 계산합니다.

① 착용 경험 입력
② 8체형 진단 결과
③ 브랜드별 추천 사이즈
1
"유니클로 오버핏 S를 입어요"
기본 정보 4개 + 평소 입던 옷 1~3벌과 부위별 느낌(끼임/딱맞음/여유/큼). 이 착용 경험이 줄자를 대신합니다.
2
내 몸을 거꾸로 계산
그 옷의 실측치에서 여유(옷−몸)를 역산 → 부위별 몸 치수 → 8체형으로 분류. 근거는 사이즈코리아 제8차 인체치수조사 회귀 모델입니다.
3
안 입어본 브랜드로 번역
계산된 몸을 9개 브랜드 · 1,679행 실측표에 대입 — 브랜드마다 다른 사이즈가 '딱맞음 %'와 병목 부위까지 함께 나옵니다.
✓
정확도 검증 루프
결과 화면의 "맞아요 / 보통 / 안 맞아요"를 진단 ID와 함께 DB에 적재 — 킬 메트릭(동의율 65%)을 실측합니다.

Behind the Screen

화면 뒤에는 정확도를 측정하고 키우는 구조가 있습니다

운영 콘솔 Supabase 실배선

"정확하다"는 말은 증명해야 하는 주장입니다. 그래서 측정 → 원인 분해 → 개선까지를 제품 안에 넣었습니다.

Step 01 · 측정

킬 메트릭 집계

모든 진단과 피드백이 진단 ID로 묶여 DB에 쌓입니다. "맞음/애매/틀림" 비율이 곧 동의율입니다.

목표 ≥ 65%
Step 02 · 분해

어디서 틀렸나

정확도를 신뢰도 × 8체형 × 브랜드 × 부위로 쪼갭니다. "확신했는데 틀린 것"이 1순위 수정 대상입니다.

캘리브레이션 히트맵
Step 03 · 개선

엔진 강화 작업목록

진단 로그(불편했던 부위·자유서술)를 사람이 할 일 목록으로 바꿉니다 — 실측 보정 · 규칙 튜닝 · 데이터 수집.

자동 학습이 아니라 우선순위
Step 04 · 성장

데이터가 스스로 는다

판정에 올라온 사이즈표를 검수 후 정본으로 승격 → 바로 다음 진단에 반영. 쓸수록 커버리지가 넓어집니다.

사용자 → 검수 → 정본 DB
엔진 정책
사이즈 숫자는 규칙으로(검증 가능), 설명 문장만 AI로 — 추천을 AI에 맡기면 맞았는지 확인할 방법이 없습니다

엔진 규칙은 골든 테스트로 잠가 두어, 고치다 예전 계산이 깨지면 즉시 드러납니다

Process · 협업

문서를 코드 옆에 두었습니다

기획 문서·화면 정의·의사결정 기록을 같은 저장소에 두고, 화면 현황판은 코드에서 자동 생성합니다.

방향이 바뀐 결정은 이유까지 기록해, 나중에 "왜 이렇게 됐지"를 다시 묻지 않습니다.

Stack · 운영비

운영비 $0으로 실서비스 구조

정적 프론트 + 서버 API + Supabase(Postgres). 브랜드 실측표는 서버에만 두어 노출되지 않게 했습니다.

진단·판정 계산도 서버에서 — 데이터가 곧 자산이기 때문입니다.
